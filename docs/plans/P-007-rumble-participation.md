# Simple Rumble participation, public Beta, and isolated development testing

This campaign serves bot authors, computing-time contributors, and the maintainer who tests Rumble. It replaces the difficult repository-and-command onboarding journey with a dedicated GUI menu and reusable headless tooling. The existing competition becomes the public Beta; a separate development Rumble is resettable without affecting participants. The maintainer requested implementation of this plan and then explicitly selected local acceptance rather than PR acceptance. This first change adopts the campaign only; product features, Beta labeling, repository creation, and bot cleanup remain outstanding below.

The corpus states no vision document. This campaign proceeds under [learning programming through competition](../goals/G-001-programming-game-for-learning-and-competition.md) and the [simple-participation goal](../goals/G-004-simple-rumble-participation.md). The [target participation design](../design/rumble/participation.md) defines shared interfaces and environment boundaries. The four linked journeys cover authoring, contribution, withdrawal, and maintainer testing; milestone changes add their executable acceptance criteria before changing behavior.

## User-facing contract and scope

- Keep **Rumble** as one top-level GUI menu: Get started; Submit or update bot; My bots; Download bots; Contribute battles; Results and queue; Rankings; GitHub account; Help. Public Rankings opens `https://robocode-dev.github.io/rumble-data/` in the default browser without sign-in; development mode opens its clearly marked test dashboard.
- A free GitHub account is needed for publishing and ranked contribution, not local creation/practice. Browser device sign-in replaces manual token handling. Only the host retains credentials; trusted workflows enforce identity and authority.
- Generate submission-ready projects in all four languages, stage existing sources without overwriting them, show files/license before publication, and retain moderation. Use the same operation for updates.
- Contributors choose all bots, prefer any selected bots, or require every battle to include at least one selected bot. Selection follows active versions, rotates fairly, and supports explicit team entries. Use one concurrent battle initially, bounded or continuous sessions, configurable resources, and durable automatic uploads with no favorable-result filter.
- Withdrawal preserves history and ownership while removing active eligibility and freeing active slots. It is distinct from disqualification. Dependent teams become ineligible; unrelated members stay active. Public cleanup is withdrawal, while only development state can be purged/reset.
- Readable bot pages preserve format and period and show useful metadata/statistics. Maintainers alone grant official sample labels. Samples remain ranked benchmarks; beating them is encouraged, never required for admission. Filtering visibility does not change APS or rank.
- Consolidate runtime code in Tank Royale while preserving separate source/data repositories and operational boundaries. Migrate configuration, client IDs, journals, receipts, replays and `myBots` preferences non-destructively. Retire duplicate client publishing only after verified replacement artifacts exist.
- The existing service is the public Beta, not disposable test infrastructure. The development Rumble has separate repositories, installations, state and a reset generation that rejects obsolete pending submissions. Ordinary installs default to public; advanced test selection remains visibly distinct.
- `https://robocode.dev/rumble/` is the canonical participant home. Review every organization repository and document disposition, including unrelated and inaccessible repositories. Keep component technical guidance beside its code and historical records unchanged.

Windows is the initial complete acceptance platform. Preserve portable interfaces and existing supported paths without claiming new Linux/macOS journey evidence. Hosted services, hosted battle workers, live viewing of contribution battles, scoring changes, and automatic strategy qualification against samples are outside this campaign. Existing physics and Bot API semantics remain unchanged. Local builds serve dependencies during development; a release must deliver actual user-facing value or a warranted correction.

## Verification and stopping conditions

The strongest uncertainty is whether narrow GitHub App permissions support outside-account publishing and automatic result intake without a service. Test that small cross-boundary path in the development Rumble before investing in full UI. A hosted broker is a credible alternative but needs a new decision. Stop the dependent implementation if the proof requires broad credentials, a desktop-embedded application secret, organization membership, moderator labeling, or undocumented maintainer intervention.

A second failure is a visually polished GUI that still exposes hidden repository or runtime repair. The cheapest usability check is the reviewed mockup followed by a short outside-account journey in each implemented vertical slice. The final Windows test fails if Git commands, hand-edited JSON, per-batch posting, or undocumented maintainer intervention are necessary. Do not disguise waiting for moderation, publication or GitHub availability as a completed operation.

M-029 delivers the initial single-command fixture harness; M-030 through M-033 extend it with their feature cases; M-037 must deliver and verify its complete matrix and automatically redacted report before M-034 documentation and M-035 release acceptance. Add real container execution where necessary. Cover all/preferred/strict scheduling, multiple entries and formats, team conflicts, unavailable selections, version transitions, pause/stop/restart, resource/container failures, registration abuse, auth expiration/revocation, duplicate uploads, partial receipts, delayed publication, withdrawal/restoration, safe metadata rendering, sample filters and credential isolation. Include positive and negative environment-isolation/reset cases. Produce a concise report with redacted diagnostics, versions, source/image identities, and receipt references automatically.

Real GitHub tests use the development environment and ordinary outside accounts. Retain a short public smoke check because development installations do not prove public permissions. Restore or reset only development fixture data; preserve public evidence and historical snapshots. The public smoke test persists a run manifest and must withdraw every temporary entry it creates before M-035 can complete, including recovery after interruption; accepted public results are retained rather than purged. Documentation checks cover builds, links, redirects, and agreement with the released GUI. Reassess the campaign when evidence changes a dependency or outcome rather than extending its promises silently.
