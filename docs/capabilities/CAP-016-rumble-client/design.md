# CAP-016 design

The external [Rumble Client repository](https://github.com/robocode-dev/rumble-client) owns the executable client, while this corpus owns its durable capability and behavioral contract. The [client architecture and result flow](../../design/rumble/client-battles-and-results.md) describe the broader design direction. The accepted [browser-form submission decision](../../decisions/ADR-049-rumble-browser-form-submission.md) replaces the original token-based submission path; its replacement criteria remain draft pending external implementation and journey evidence. The planned desktop screens that sit on top of this client are drafted in the [Rumble menu mockups](../../design/rumble/gui-mockups.md).

## Configuration and synchronized snapshot

One versioned configuration selects `ranked` or `practice`, the initial bot and data repository locations, a stable client ID for ranked mode, optional own-bot scheduling hints, selected V1 game types, a positive battle count, and local cache, journal, and evidence locations. Configuration validation completes before network, battle, journal, or submission side effects.

A ranked session begins from the configured data repository's `wellknown/rumble.json` and follows its canonical location. From one data-repository revision it reads `engine.json`, `catalog.json`, `clients/<forge-account>.json`, and `matchmaking/matches_needed-<game-type>.json` for each selected game type. The client rejects unknown schema versions, an unregistered client ID, unsupported game types, inconsistent projections, or a catalog whose declared source commit cannot identify the reviewed source in [CAP-014](../CAP-014-rumble-bot-catalog/README.md).

The accepted snapshot pins all ranked work in the session. Cached bot source is addressed by the catalog's immutable `sourceCommit` and each entry's `sourceHash`; a hash disagreement rejects the bot before execution. Individual entries have no team members. A TwinDuel team entry names exactly two active individual catalog identities in `teamMembers`, preserving repeated member slots, and cache preparation obtains and verifies the team entry plus each referenced member source tree. Matchmaking files are advice rather than reservations, so seeded selection may safely fall back to other eligible entries. `1v1` and `melee` select distinct individuals; `twinduel` selects two distinct team entries whose expanded member count equals the engine pin's participant count and whose member-identity sets are disjoint.

## Execution and mode boundary

Battle Runner [CAP-001](../CAP-001-battle-runner/README.md) owns server lifecycle, bot processes, identity matching, full-round execution, and `BattleResults`. The client owns synchronization, source preparation, selection, result transcription, replay retention, journaling, and submission.

Ranked mode accepts only active pinned catalog sources and requires the running server's advertised `behaviorVersion` to equal `engine.json`. Practice mode may use local unpublished sources and a different engine, but it has no path to the ranked journal or submission transport. This separation is part of the trust boundary, not a presentation option.

## Choosing the next battle of a session

A contribution session asks `SessionPlanner` in the shared library for its next battle and records each finished battle in the session history it passes back. The planner answers with a battle, a wait with a reason code, or that the session is finished. The three modes are all bots (the selection is ignored), prefer selected bots (a valid battle with a selected entry first, otherwise any valid battle) and only selected bots (every battle holds a selected entry; with none valid it waits and says why, and a wait the whole catalog caused is told apart from one only the selection caused). Missing or unusable advice blocks nothing, and a complete advised group decides the battle before the coverage so far does, while a short one is filled up by coverage. The planner has no screen, worker, network or clock, which is what makes it provable alone and the same in the desktop program and the command line.

## The ranked journal in the shared library

The journal contract below is kept by `RankedJournal`: one file per environment, a header, one record line per completed ranked battle and a move line for each change of a record's state (waiting, handed over, accepted, rejected, set aside). Only lines are added; nothing written is changed. A torn last line from an interrupted write is reported and never read as a record, and the next line is started on a fresh line. The same battle ID is kept once. A waiting record made on another behavior version than the Rumble's current pin is set aside with its reason and stays available. The batches, the receipts and the screens that move records are later parts built on this.

## Running a session's battles

`SessionRunner` joins the planner, the bot cache, the worker host and the journal. It runs one battle at a time, places each chosen bot by its source hash with a team's members beside the team, keeps a result only when the worker completed the battle, and makes the record from the job and the result alone. A battle that did not complete, a bot that could not be placed and a result that does not match the bots or rounds that ran each give a plain event with a reason code and no record. A bot that can never be placed from the commit is left out for the session; a source that cannot be reached is tried again and counts towards giving up. Pause, finish-and-stop and cancel-now come through a control that any thread may set; cancel-now ends the worker process tree and keeps nothing of the battle. The engine pin and the advice come from the environment's result repository: `SessionPins` reads `engine.json` and refuses a session before any battle when the pin cannot be read or understood, or when this program cannot run under it (another behavior version, a format the pin does not name, or a battlefield or participant count the battle worker does not run), naming the pin's value and this program's; otherwise the session runs the pin's rounds and battle sizes with its behavior version. `AdviceKeeper` reads each format's needed-battles file as optional advice, read again only after a refresh time, and a failed read keeps the last advice.

## Sending results and reading receipts

`ResultUploader` sends the journal's waiting records of the current engine epoch as the signed-in contributor, under the decision on signed-in sending: batches of one client each, one to sixty records and at most 50,000 characters of envelope, in the record shape the result data validates, each opened as one `[result]` issue with a unique title and exactly one fenced `json` envelope. A batch's records are handed over in the journal before its issue is opened, and `SentBatches`, a file that is only added to, records each batch before it is sent and the issue it became, so a crash never loses a record: a batch that never became an issue is sent again. A send GitHub refuses returns its records to waiting with a reason code; a send with no clear answer keeps the batch handed over and sends it again under its own identity, which the Rumble answers like the first. Receipts are read from the receiving workflow's own comments only, page by page; each record is accepted, rejected with the receipt's reason, or sent again when the receipt does not name it or its issue is gone, and a batch refused before its records could be read waits again and stops sending, recorded in the same file so the stop holds after a restart until the contributor lifts it. Records of a format the pin no longer names wait while the others are sent. Without a usable sign-in, with a pin that refuses this program, or for a record without a client ID, nothing is sent and the reason is given. `AutomaticUpload` sends between a session's battles when enough results wait or after a set time, never twice within a short gap, and collects receipts at its own interval; a failure of sending other than an unwritable journal is reported and never ends the session.

The worker is started so that a Ctrl+C in the contributor's terminal does not reach it or the bots it starts: on Windows through `start /b`, which runs a program with Ctrl+C ignored and passes that on to its children (shown with a real console Ctrl+C on 2026-11-16), elsewhere through `sh` with `trap '' INT`, an ignored signal that every child keeps. On Windows the arguments reach `cmd` in variables read with delayed expansion, never in its command line, so paths with `&`, `^`, `%` or `!` are used as they are. A program that is not there, or elsewhere cannot be run, is still reported as not started.

Under the [decision that each ranked battle with a Python bot gets its own copy of the program's Python Bot API](../../decisions/ADR-056-ranked-python-battles-get-their-own-bot-api-copy.md), `SessionPython` installs the program's own Python Bot API, with only `websockets` and `pycountry`, which it imports when a bot runs, at the version bounds and under the file name the wheel's own metadata gives, into a new folder of the session's own, held by a lock file taken before the folder is made and kept while the session lives, so the next session removes only the folders of sessions that ended without closing and never another session's lock file, with the contributor's Python at the supported version, keeps the digest in memory, and removes the folder when the session ends. For every battle that holds a Python bot, the session's `battleEnvironment` copies the folder into a new folder of the battle's own that is not the bots' temporary folder and checks the copy against the digest, read file by file so tens of megabytes are never held in memory; a copy that does not match means the session's folder changed, and it is installed again and copied once more. The session then gives the worker the copy on `PYTHONPATH` with `PYTHONNOUSERSITE`, `PYTHONDONTWRITEBYTECODE` and `RUMBLE_PYTHON`; the worker host takes such variables from a hook that gets the battle's folders, and any failure there makes the battle not start with its own reason. The command line carries the wheel built with it, the newest in the Bot API's build folder, whatever form Python gives its version. Without the Rumble's list of versions, the wheel's own lowest Python is required. A copy that can no longer be made leaves the session's Python bots out for the rest of the session, and a Ctrl+C while Python is set up is reported as a stop. On 2026-11-17 the install took about 3 seconds and the folder is 24 MB in 842 files, mostly pycountry's locale data; a copy took about one second.

## Result, evidence, and journal contracts

After a full ranked battle completes, the client creates the V1 envelope record consumed by [CAP-015](../CAP-015-rumble-result-data/README.md): a UUID battle ID, ISO-8601 completion time, matching client identity and version, pinned behavior version, game type and dimensions, and the complete Battle Runner participant result model. The client stores the replay as local evidence addressed by the battle ID and records its SHA-256 hash locally; replay files are not submitted to `rumble-data` in V1.

The append-only local journal is the durability boundary between execution and transport. A completed ranked record is durable before submission begins. The result-data workflow publishes a successful per-result receipt only after the accepted fact commit reaches the canonical repository; retrying an identical retained result returns the same successful outcome. The client removes only records covered by those receipts. Interruption, partial rejection, authentication failure, rate limiting, and publication failure preserve the remaining queue for retry. A later engine-pin change quarantines queued records from another behavior-version epoch instead of submitting incompatible facts.

## Submission and credential boundary

V1 uses the issue-ops contract implemented by [Rumble Data](https://github.com/robocode-dev/rumble-data). The client prepares every compatible pending record in complete batches of one to sixty results, also splitting by serialized size so that the fenced envelope fits comfortably within the issue body limit. Each batch is handed to the contributor as plain text, through a file or clipboard, containing exactly one fenced `json` envelope. A rendered Markdown view is not the handoff because copying it can drop the required fences.

The client prints or opens the result form address with only a unique batch title prefilled. The contributor signs in to the registered GitHub account, pastes the complete unchanged batch and creates the issue; the form supplies the `result-submission` label. A free personal account and merged client registration are required; organization membership, push access and a submission token are unnecessary.

Preparing a batch is not acceptance. Prepared batches and their journal records remain retryable across reruns and interruption. The client discovers the posted issue, reads its public ingestion receipts without a credential, correlates successful receipts to the original journal records and acknowledges only those records. Anonymous rate limiting, absent issues, incomplete receipts or publication failure preserve the outstanding records. Terminally rejected records remain available for diagnosis and retry rather than being discarded. The publication-first acknowledgement and identical-retry semantics above are unchanged.

Accounts with repository push access may optionally submit through the API using an Issues-only credential under the trust-boundary decision. This is a privileged convenience, not a required client mode or an alternative supported onboarding path for outside contributors. The browser-form decision leaves a GitHub App for separate evaluation; no authentication service is introduced here.

Fork-pull-request submission remains a portability option only after the result-data capability publishes and validates that transport. `rumble-data` explicitly does not support it in V1, so M-008 does not claim it as an available fallback.

### Planned replacement: signed-in participation from the desktop program

The browser-form hand-off above is the supported client today and stays so until its replacement is accepted. The replacement is described in the [participation design](../../design/rumble/participation.md): the desktop program and a headless controller sign the contributor in to GitHub with a short code and renew that sign-in without a client secret, register the account automatically, and send results and bot submissions as the signed-in account, as the [outside-account experiment](../../analysis/AN-023-outside-account-sign-in-experiment.md) showed to work. The sign-in is saved between runs in one protected file in the Tank Royale user folder, the same on every operating system, as the [experiment on saving the sign-in](../../analysis/AN-024-saving-the-github-sign-in-in-one-java-only-file.md) tested. The decision that a signed-in contributor's program sends its batches and reads their receipts itself, [ADR-055](../../decisions/ADR-055-signed-in-contributors-send-rumble-results.md), revises the credential part of the web-form decision for that path. The sign-in, renewal, saved sign-in, registration and sending of results already exist in the shared Rumble library; the screens do not. Only the host side holds the sign-in; battle workers never receive it.

## Runtime boundary

The primary distribution is a rebuildable container containing the pinned Tank Royale engine, Battle Runner, and the Java, .NET, Python, and Node.js runtimes required by the catalog. The image follows an LTS-first runtime policy; the external Rumble client repository owns the exact pins and its scheduled refresh workflow opens a reviewable pull request only after the image, hardened checks, and all four language smoke battles pass. Client network egress is limited to repository synchronization and issue submission; bot processes receive only the local server connection. Documented bare-metal setup remains available with an explicit warning that it does not provide the container boundary.
